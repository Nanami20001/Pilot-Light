# SL25 Rev B 固件排查结果

## 结论

排查时的旧状态灯 HEX 存在可导致灯不亮的 WS2812 时序错误。USB ISP 烧录校验只能覆盖 Bootloader 下载通路。

旧 HEX 的 SHA256 是 `37D3D69CFFE4621E03CFA741BAF6593F89FAA598A22F2D08876D4FF2FBB15C47`。本地旧构建和排查证据归档在 `archive/2026-11-25/ch552_codex_status/`。当前交付用 `ch552_codex_status/build/sl25_codex_status.hex`。

## 已确认并修复

1. `__asm nop; nop; ... __endasm` 中的分号在 SDCC 汇编里开始注释，后续 NOP 没有生成机器码。原来逻辑 1 的高电平按 WCH 指令周期估算仅约 250 ns，低于 WS2812B-V5 要求的 580 ns；逐位 C 函数调用和循环还使低电平时长失控。已替换为预先展开 24 位 GRB、固定汇编循环发送。
2. 发送函数原来无条件开启全局中断，可能破坏调用者的初始化状态。现保存并恢复 EA，并在启动时先置低数据脚、等待电源稳定再发送。
3. USB 控制端点原来接受 HID `SET_REPORT`，但没有将随后收到的 Output 报告写入灯光状态。现处理接口 0、报告 ID 0、类型 Output、长度 8 的报文，并正确发送 DATA1 状态包；非法请求返回 STALL。原有 EP2 interrupt OUT 保留。
4. 主循环读取报文和 16 位时间戳时原来可能被 USB 中断打断。现统一在短临界区内读取；USB 总线复位时清除旧灯光状态和未完成的控制报文。

状态灯固件自检后默认熄灭，收到有效主机状态报文后才持续显示。超过 3 秒无新报文会熄灭。这是现有应用行为，不能用“烧完后不常亮”单独判断故障。

## 推荐实物验证顺序

1. 烧录 `ch552_led_diagnostic/build/sl25_led_diagnostic.hex`，下载并校验。
2. 拔 USB、松开 JP1/BOOT、重新插入。预期红/绿/蓝/灭各约 1 秒循环。诊断程序没有 USB 应用枚举，这是预期行为。
3. 诊断成功后，烧录 `ch552_codex_status/build/sl25_codex_status.hex`，松开 JP1 并重新上电。程序会短暂白光自检，然后等待主机报文。
4. 使用原有主机代理发送工作状态。若自检或独立诊断正常、主机控制不正常，再查看 HID 枚举、驱动绑定和实际发送报文。

## 电压问题的边界

当前电路的 LED VDD 与 USB VBUS 同属 +5V 网络，软件没有控制这一电源的开关或稳压器。被检查的应用源码也没有写 `GLOBAL_CFG.bLDO3V3_OFF` 来关闭内部 V33 稳压器。因此上述代码错误能解释灯不亮，不能据此断言已解释或修复 2.5 V / 1.66 V。真实欠压仍需用可靠电压测量确认；负载异常也可能间接拉低供电。

## 验证

- SDCC 4.6.2：状态灯程序和独立诊断程序均编译、链接成功，HEX 校验和有效，地址未进入 0x3800 及以上的 ISP 保留区。
- `verify_ws2812.py` 对每个最终 HEX 的发送机器码检查 261 组帧，覆盖所有字节值。采用 WCH 指令周期和 23.64～24.36 MHz 时钟范围核算。该检查不模拟电气波形。
- 当前两份 HEX 在 24 MHz 下，T0H≈333 ns、T1H≈625 ns、T0L≈917 ns、T1L≈625 ns；锁存低电平在最快时钟下仍超过 490 µs。
- `test_firmware_logic.py` 在模拟寄存器变量上执行实际 C 请求处理代码，检查控制 OUT、EP2 OUT、状态阶段、非法/被中止的报文、超时、总线复位及描述符长度。它不模拟 USB 硬件或写 1 清零寄存器。
- 2026-11-25 样机已装配并成功显示灯光。当前记录未包含烧录文件的校验值、USB 事务记录或示波器波形。
